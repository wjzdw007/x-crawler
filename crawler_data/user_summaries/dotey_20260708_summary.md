**新工具/技术**（如有）
- GPT-5.6 / Sol — OpenAI 即将公开推出的模型（7/9 附近），Sol 表现更通用、更快速、交互更“愉快”。  
- Fable — 更偏向高度针对性的调试/安全/性能任务，是“专精型”模型。  
- SkillsBench（Skill 评估框架）— 用三种条件（无 Skill、专家策划 Skill、模型自生成 Skill）系统比较技能效果的评测方法。

**核心观点/方法论**（如有）
- 人+AI 协作写 Skill 优于让模型独立生成 — 模型能写 Skill，但需要人提供高质量上下文与引导，否则效果不稳定。  
- 小而聚焦胜过大而全 — 仅包含 2–3 个文件、范围明确的 Skill 通常优于“百科全书式”的全面 Skill。  
- 加载越多 Skill 反而占用上下文并可能降低整体性能 — 要按需加载，避免堆栈式塞入大量技能。  
- 每个 Harness（不同 Agent/模型）都要单独测试兼容性 — 不同模型具备不同能力（多模态、内置工具等），需针对性适配。  
- 瞄准模型薄弱领域产出最大收益 — 若模型在某领域训练数据少（如医疗、制造），Skill 带来的提升更明显；代码领域增益较小。  
- 强调严格的 A/B 测试流程 — 在相同任务集上对比加载/不加载 Skill 的结果，量化效果。

**实践经验/案例**（如有）
- dotey 的实践倾向：不常用软件工程类 Skill（模型已被大量代码训练），更看重在训练薄弱领域的 Skill。  
- 最佳实践：人来设计结构与上下文，AI 来生成/固化操作路径与输出格式——“人指挥 AI 写 Skill”。  
- 测试策略：上线前用统一任务集做两次对比（加载 vs 不加载），并结合专业判断处理难以量化的指标。  
- Mitchell 的实测示例：Sol 为默认首选（通用性与工作体验更好），Fable 在高度针对性调试/安全/性能任务上更强。  
- 招聘/项目建议（转发观点）：求职者应打磨一个有深度的项目，展示完整尝试、benchmark 与结论，比做大量浅项目更有价值。
